## 3. Explanation of Each Technical Correction

### 3.1. Correction P0-01 (Security Architecture & Identity Boundary)
- **Problem:** Client-controlled HTTP request headers (like `X-User-Id`) provide zero assurance of identity provenance because any client or attacker can manipulate them. Calling this "authentication" in a course teaching software engineering is a pedagogical and architectural error.
- **Correction:** The production teaching app is architecturally defined as a **single-tenant team workspace with NO authentication**, matching the actual requirements of Slots 1–3 and Slot 5. In Slot 4, where the curriculum teaches Broken Access Control (IDOR), identity simulation is quarantined inside a dedicated development fixture (`src/fixtures/simulated-auth.ts`). This fixture is hard-coded to check `process.env.NODE_ENV === 'production'` and throw an unrecoverable startup error if ever enabled in production.

### 3.2. Correction P0-02 (Task Priority Attribution)
- **Problem:** P0 asserted that Slot 1 Slide 17 and Lab 01 require implementing Task Priority (`LOW`, `MEDIUM`, `HIGH`). Slide XML analysis showed neither slide mentions priority; both require a generic controlled AI change. Pre-implementing priority in Slot 1 would also undermine Slot 2, which teaches controlled feature branching and scope management.
- **Correction:** Task Priority was stripped from all Slot 1 specifications. Slot 1 demonstrates a generic change (such as an optional description field or input sanitization). Task Priority is cataloged strictly as an optional demonstration example in Slot 2, preserving the planned deadline-editing planning challenge (`dueDate`).

### 3.3. Correction P0-03 (Demo and Lab Inventory Counts)
- **Problem:** Previous reports claimed "14 live demos" and "15 student labs", conflating explicitly labeled slides with unlabelled activities and assessments.
- **Correction:** Reconciled counts against the slide text:
  - Decks contain **9 explicitly titled Live Demo slides**, plus **1 live incident drill** (Slot 5 Slide 15). Adding 4 unlabelled but necessary instructor demonstrations yields the 14 planned demos. All 4 unlabelled items are explicitly tagged `[SUPPLEMENTARY PLANNED DEMO]`.
  - Decks contain **12 explicitly labeled student labs** across Slots 1–4. Slot 5 contains **2 guided practical activities** and **1 summative Demo Day oral defense assessment**. The total is accurately reported as **14 guided labs/activities + 1 Demo Day assessment**.

### 3.4. Correction P0-04 (Design vs. Implementation Status)
- **Problem:** Earlier text stated checkpoints, reset scripts, and tests were "verified" or "existing", but HEAD contained only markdown files.
- **Correction:** All references to non-existent tags, branches, files, and commands have been prefixed with `[PLANNED]`. The P0 deliverables are explicitly identified as approved implementation designs, not completed executable code.

### 3.5. Correction P0-05 (Checkpoint Safety & Safe Recovery)
- **Problem:** Running `git reset --hard` and `git clean -fd` destroys uncommitted student or instructor work.
- **Correction:** Checkpoint navigation is redesigned around **disposable Git worktrees** (`git worktree add`). For in-place resets, a planned Node.js script enforces `--dry-run` by default, requires `--force`, and checks for dirty Git state with `--stash` snapshot support.

### 3.6. Correction P0-06 (Database & Deployment Reference Architecture)
- **Problem:** Suggesting that SQLite and PostgreSQL migrations can be swapped by editing the Prisma provider in place is error-prone. Leaving hosting undecided created ambiguity.
- **Correction:** Decided reference stack: **Vercel** (web), **Render** (API), **Neon PostgreSQL** (database). Separated database schemas into `prisma/schema.sqlite.prisma` (local) and `prisma/schema.postgres.prisma` (cloud), with CI-driven migration rehearsal against Neon.

### 3.7. Correction P0-07 (Unverified Claims & Prerequisites)
- **Problem:** Specific URLs, ports, and sub-second recovery claims were stated as fact without execution.
- **Correction:** Labeled URLs and ports as planned examples. Documented prerequisites (Node.js, Playwright Chromium, Semgrep, cloud credentials) and defined an offline classroom fallback for every slot.

### 3.8. Correction P0-08 (P0 Report Accuracy)
- **Problem:** Stating that P0 was "strictly completed" obscured the fact that implementation code and executable verification remain pending.
- **Correction:** Updated `reports/P0-verification.md` and `PHASE_REPORT.md` with the required wording: *"Documentation discovery and curriculum inventory completed. Executable implementation, checkpoint validation and runtime verification remain pending."*

## 4. Remaining Architecture Risks & Mitigations

1. **Classroom Connectivity Failure:**
   - *Risk:* If student or campus Wi-Fi degrades during Slot 5, cloud deployments to Vercel/Render/Neon could stall.
   - *Mitigation:* Built-in offline containerized deployment simulation using local Docker Compose and local PostgreSQL.
2. **Playwright Browser Installation Friction:**
   - *Risk:* Students on corporate or restricted laptops may experience failures downloading Playwright Chromium binaries.
   - *Mitigation:* Pre-flight verification in Slot 1 and headless Supertest integration tests as a primary automated testing baseline.
3. **Student Team Project Scope Divergence:**
   - *Risk:* Student teams building independent projects may deviate from the required testing or CI patterns.
   - *Mitigation:* Milestone validation scripts (`check-submission.mjs`) will enforce structural rules (PRD, PR format, test presence) independently of project domain.
